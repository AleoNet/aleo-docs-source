# Cryptographic Operations

These operations are available in `function`, `closure`, and `finalize` blocks.

## Group Generators

| Operand | Type | Description |
|---------|------|-------------|
| `group::GEN` | `group` | Generator of the prime-order subgroup for the Twisted Edwards curve |
| `aleo::GENERATOR` | `group` | The point `G` used for Aleo account derivation (`view_key * G = address`) |
| `aleo::GENERATOR_POWERS[Nu32]` | `group` | Array of 253 group bases (indices `0u32`–`252u32`) for signature and encryption schemes |

`aleo::GENERATOR` is equivalent to `aleo::GENERATOR_POWERS[0u32]`. All bases are generated by calling `hash_to_curve` on the domain string `"AleoAccountEncryptionAndSignatureScheme0"`.

## Commit

Commitments take a plaintext value and a `scalar` randomizer, producing an `Address`, `Field`, or `Group`.

| Opcode | Description |
|--------|-------------|
| `commit.bhp256` | BHP commitment with 256-bit chunks |
| `commit.bhp512` | BHP commitment with 512-bit chunks |
| `commit.bhp768` | BHP commitment with 768-bit chunks |
| `commit.bhp1024` | BHP commitment with 1024-bit chunks |
| `commit.ped64` | Pedersen commitment, up to 64-bit input |
| `commit.ped128` | Pedersen commitment, up to 128-bit input |

```aleo
commit.bhp256 r0 r1 into r2 as field;
```

## Hash

Hash opcodes take a plaintext value and produce an `Address`, `Field`, or `Group` (or for `hash_many`, multiple fields). Variants exist for most algorithms:

- **Standard** (`hash.X`) — hashes Aleo-variant-encoded bits
- **Raw** (`hash.X.raw`) — hashes raw bits/fields *(V11)*
- **Native** (`hash.X.native`) — outputs the native bit array instead of mapping to a field *(V11)*
- **Native raw** (`hash.X.native.raw`) — raw input, native output *(V11)*

| Algorithm | Standard | Raw | Native | Native Raw |
|-----------|----------|-----|--------|------------|
| BHP-256 | `hash.bhp256` | `hash.bhp256.raw` | — | — |
| BHP-512 | `hash.bhp512` | `hash.bhp512.raw` | — | — |
| BHP-768 | `hash.bhp768` | `hash.bhp768.raw` | — | — |
| BHP-1024 | `hash.bhp1024` | `hash.bhp1024.raw` | — | — |
| Pedersen-64 | `hash.ped64` | `hash.ped64.raw` | — | — |
| Pedersen-128 | `hash.ped128` | `hash.ped128.raw` | — | — |
| Poseidon-2 | `hash.psd2` | `hash.psd2.raw` | — | — |
| Poseidon-4 | `hash.psd4` | `hash.psd4.raw` | — | — |
| Poseidon-8 | `hash.psd8` | `hash.psd8.raw` | — | — |
| Keccak-256 | `hash.keccak256` | `hash.keccak256.raw` | `hash.keccak256.native` | `hash.keccak256.native.raw` |
| Keccak-384 | `hash.keccak384` | `hash.keccak384.raw` | `hash.keccak384.native` | `hash.keccak384.native.raw` |
| Keccak-512 | `hash.keccak512` | `hash.keccak512.raw` | `hash.keccak512.native` | `hash.keccak512.native.raw` |
| SHA3-256 | `hash.sha3_256` | `hash.sha3_256.raw` | `hash.sha3_256.native` | `hash.sha3_256.native.raw` |
| SHA3-384 | `hash.sha3_384` | `hash.sha3_384.raw` | `hash.sha3_384.native` | `hash.sha3_384.native.raw` |
| SHA3-512 | `hash.sha3_512` | `hash.sha3_512.raw` | `hash.sha3_512.native` | `hash.sha3_512.native.raw` |

Additionally, `hash_many.psd2`, `hash_many.psd4`, and `hash_many.psd8` produce multiple field elements from a single input.

```aleo
hash.bhp256 r0 into r1 as field;
hash.keccak256.native r0 into r1 as [boolean; 256u32];
```

## Signature Verification

| Opcode | Description |
|--------|-------------|
| `sign.verify` | Verifies a Schnorr signature: `sign.verify {signature} {address} {message} into {destination}` → Boolean |

## ECDSA Verification

*Added in Consensus V11.*

ECDSA opcodes verify secp256k1 signatures against Aleo addresses or Ethereum 20-byte addresses. Each hash algorithm has standard, raw, and Ethereum variants:

| Hash Algorithm | Standard | Raw | Ethereum |
|---------------|----------|-----|----------|
| Digest (precomputed) | `ecdsa.verify.digest` | — | `ecdsa.verify.digest.eth` |
| Keccak-256 | `ecdsa.verify.keccak256` | `ecdsa.verify.keccak256.raw` | `ecdsa.verify.keccak256.eth` |
| Keccak-384 | `ecdsa.verify.keccak384` | `ecdsa.verify.keccak384.raw` | `ecdsa.verify.keccak384.eth` |
| Keccak-512 | `ecdsa.verify.keccak512` | `ecdsa.verify.keccak512.raw` | `ecdsa.verify.keccak512.eth` |
| SHA3-256 | `ecdsa.verify.sha3_256` | `ecdsa.verify.sha3_256.raw` | `ecdsa.verify.sha3_256.eth` |
| SHA3-384 | `ecdsa.verify.sha3_384` | `ecdsa.verify.sha3_384.raw` | `ecdsa.verify.sha3_384.eth` |
| SHA3-512 | `ecdsa.verify.sha3_512` | `ecdsa.verify.sha3_512.raw` | `ecdsa.verify.sha3_512.eth` |

All ECDSA opcodes take 3 operands (signature, address, message) and return a Boolean.

## SNARK Verification

*Added in Consensus V14 ([ARC-0008](https://vote.aleo.org/p/arc-0008)).*

Currently limited to Varuna proofs, with the possibility to extend to other proof systems in the future. Both opcodes are **finalize-only** and must be called within a `finalize` block.

| Opcode | Description |
|--------|-------------|
| `snark.verify` | Verifies a single SNARK proof |
| `snark.verify.batch` | Batch verification of multiple SNARK proofs |

### `snark.verify`

Verifies a Varuna proof against a verifying key and the public inputs, storing the boolean result in the destination register.

```aleo
snark.verify r0 r1 r2 into r3;
```

| Operand | Type | Description |
|---------|------|-------------|
| `r0` | `[U8; N]` | Verifying key |
| `r1` | `[Field; M]` | Public inputs |
| `r2` | `[U8; P]` | Proof |
| `r3` | `Boolean` | Verification result |

### `snark.verify.batch`

Batch-verifies multiple Varuna proofs against an array of verifying keys, a nested array of public inputs, and a single batch proof.

```aleo
snark.verify.batch r0 r1 r2 into r3;
```

| Operand | Type | Description |
|---------|------|-------------|
| `r0` | `[[U8; N]; num_keys]` | Array of verifying keys |
| `r1` | `[[[Field; M]; num_instances]; num_keys]` | Nested array of public inputs per circuit per key |
| `r2` | `[U8; P]` | Batch proof |
| `r3` | `Boolean` | Batch verification result |

Compile-time limits apply: **maximum 32 circuits, maximum 128 total instances** across all circuits.
