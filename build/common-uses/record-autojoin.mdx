# Record Autojoin

Aleo's private balances are stored as **records** — encrypted UTXOs that only the owner can decrypt. A wallet's private balance is the sum of the records it holds. Routine activity (sending, receiving, paying fees) accumulates many small records over time, a condition known as **record fragmentation**.

![Fragmented vs. consolidated wallet: many small records become one](/img/autojoin/01-fragmentation.svg)

A fragmented wallet may hold enough total balance to cover a given payment and still be unable to send that payment in a single transaction. The payment could be broken into several smaller transactions, but then each smaller payment would incur its own fee.

Because records are private and only spendable by their owner, the protocol cannot automatically aggregate them on the user's behalf. Therefore, wallet providers who wish to integrate Aleo must handle this record management and consolidation at the application layer.


A canonical reference implementation is available at [AleoNet/example-autojoin](https://github.com/AleoNet/example-autojoin). 

## The `Join` Primitive

Every officially recognized token program on the network defines a `join` transition that consumes two existing records and produces one output record whose amount equals their sum. Repeated applications of `join` reduce any number of records to a single record.
## Pairwise Reduction

The simplest strategy: group records into pairs, join each pair, then repeat on the outputs until one record remains.

<img src="/img/autojoin/02a-pairwise.svg" alt="Pairwise joins" style={{display: 'block', maxWidth: '640px', margin: '1.5rem auto'}} />

```typescript
const pairs: [AleoRecord, AleoRecord][] = [];
for (let i = 0; i + 1 < current.length; i += 2) {
  pairs.push([current[i], current[i + 1]]);
}

const joinedRecords = await Promise.all(pairs.map(async ([a, b]) => {
  const { transactionId, newRecord } = await this.join2(a, b);
  await this.aleoClient.waitForTransactionConfirmation(transactionId);
  return newRecord;
}));
```

Each round can dispatch all pair joins concurrently, so the wall-clock duration of a round is roughly the duration of a single transaction. Pairwise reduction requires `N − 1` `join` transactions to consolidate `N` records — transaction count is linear in `N`, total wall-clock time is logarithmic ( $$log_2$$ ) in `N`.

The advantage of pairwise reduction is that it works with **any** token whose program exposes the standard `join` transition. No additional onchain programs are required.

## Batch Reduction

For larger record sets, pairwise reduction becomes time-inefficient. Custom wrapper programs expose a family of higher-arity transitions — `join_2` through `join_16` — that consume up to 16 records (snarkVM's per-transaction input cap) and produce one record in a single transition.

```leo
import credits.aleo;

program batch_join_credits.aleo {
    fn join_3(
        token_1: credits.aleo::credits,
        token_2: credits.aleo::credits,
        token_3: credits.aleo::credits,
    ) -> credits.aleo::credits {
        let i1 = credits.aleo::join(token_1, token_2);
        let output = credits.aleo::join(token_3, i1);
        return output;
    }

    fn join_4(
        token_1: credits.aleo::credits,
        token_2: credits.aleo::credits,
        token_3: credits.aleo::credits,
        token_4: credits.aleo::credits,
    ) -> credits.aleo::credits {
        let i1 = credits.aleo::join(token_1, token_2);
        let i2 = credits.aleo::join(token_3, token_4);
        let output = credits.aleo::join(i1, i2);
        return output;
    }

    // join_5 ... join_16
}
```

A `join_N` call net-removes `N − 1` records per transaction. With `join_16`, a consolidation of 100 records that would require 99 pairwise transactions completes in 7 batch transactions distributed over two rounds. For typical user wallets, the batch strategy terminates in one or two rounds.

<img src="/img/autojoin/02b-batch.svg" alt="Batch joins" style={{display: 'block', maxWidth: '640px', margin: '1.5rem auto'}} />

The driver loop partitions inputs into batches of up to 16, dispatches them concurrently, then recurses on the outputs:

```typescript
while (current.length > 1) {
  const batches: AleoRecord[][] = [];
  while (current.length > 0) {
    batches.push(current.splice(0, Math.min(current.length, 16)));
  }

  const joinedRecords = await Promise.all(batches.map(async (batch) => {
    const { transactionId, newRecord } = await this.joinN(batch);
    await this.aleoClient.waitForTransactionConfirmation(transactionId);
    return newRecord;
  }));

  current = joinedRecords;
}
```

The cost is the wrapper program itself — batch joins only work for tokens that have a deployed batch wrapper. `credits.aleo`, USDCx, and USAD have wrappers today. A generic dynamic-dispatch batch wrapper is expected later in 2026.

| | Pairwise | Batch |
|---|---|---|
| Works with any `join` token | Yes | No — requires a batch wrapper |
| Records per transaction | 2 | 2–16 |
| Rounds to consolidate `N` records | `⌈log₂ N⌉` | `⌈log₁₆ N⌉` |
| Per-transaction fee | Lowest (bare `join`) | Higher per call, fewer calls |

## Intermediate State and Retries

After a join is broadcast, its output record is needed as input to the next round. Re-scanning the chain between rounds would round-trip through a record scanning service; instead, the strategy decrypts the output ciphertext from the broadcast response and forwards the resulting record in memory.

Some transactions in the next round may initially be rejected if the broadcast node hasn't observed the prior transaction as finalized yet. Bounded exponential backoff handles this:

```typescript
async submitProvingRequestwithRetries(provingRequest, retries, attempts = 0) {
  try {
    return await this.submitProvingRequest(provingRequest);
  } catch (e) {
    if (retries <= 0) throw e;
    await sleep(5000 * (attempts + 1));
    return this.submitProvingRequestwithRetries(provingRequest, retries - 1, attempts + 1);
  }
}
```

## Private Fees

Aleo transactions can pay their fee either from a public balance or from a private credits record. Private-fee mode keeps the fee payment encrypted alongside the rest of the transaction, but introduces two extra constraints for autojoin.

### Input Cap

The private fee record occupies one of the 16 input slots that would otherwise be available to the function being executed. The largest batch join that fits alongside a private fee is therefore `join_15` — 15 record inputs plus 1 fee record fills all 16 slots.

For consolidating `N` records under private fees, the number of `join_15` calls needed is

$$
\large \left\lfloor \frac{N - 1}{14} \right\rfloor
$$

followed by a single `join_X` cleanup, where

$$
\large X = ((N - 1) \bmod 14) + 1
$$

The divisor is 14, not 15, because each `join_15` invocation consumes 15 records and produces 1 — a net reduction of 14.

### Fee Precision

A private fee record must hold **exactly** the amount needed for the operation it pays for. Underpayment makes the transaction fail at execution time. Overpayment returns a residual record — which itself contributes to fragmentation. Aleo fees are deterministic (set at compile time by the circuit's complexity, no congestion pricing), so the full fee budget can be computed up front.

The fee records are prepared in two splits of an existing credits record: one split carves out a master fee record sized for the total budget, the second split divides that master into per-operation fee records sized for each individual join.

![Private fee preparation pipeline: split a credits record into a master fee record, then split that into per-operation fee records](/img/autojoin/03-private-fee-pipeline.svg)

### Implicit split cost

The `split` operation on `credits.aleo` does **not** incur a normal onchain execution fee. Instead, it has an implicit **10,000 μALEO** cost deducted directly from the record being split. This is fixed by the protocol and is not represented as a separate fee record. A budget that accounts only for join fees, ignoring the splits required to prepare them, will under-fund the operation. Both quantities are deterministic and can be folded into the same up-front calculation.

## Library Usage

The reference implementation exposes two main classes:

- **`AleoClient`** — wraps the Provable SDK: network init, JWT auth, record scanning, delegated proving.
- **`AutoJoinClient`** — orchestrates the consolidation using a pluggable `JoinStrategy`.

Two strategies ship out of the box: `BasicAutoJoinStrategy` (pairwise) and `BatchAutoJoinStrategy` (uses the deployed batch wrappers). Both implement a small interface that any custom strategy can extend:

```typescript
interface JoinStrategy {
  isSupportedProgram(programName: string): boolean;
  joinRecords(records: AleoRecord[]): Promise<AleoRecord>;
}
```

End-to-end usage:

```typescript
import { AleoClient } from './src/aleo/aleoClient';
import { AutoJoinClient } from './src/aleo/autojoin/autoJoinClient';
import { BasicAutoJoinStrategy } from './src/aleo/autojoin/strategies/basicAutoJoinStrategy';

const aleoClient = new AleoClient('testnet', {
  apiKey: 'YOUR_API_KEY',
  consumerId: 'YOUR_CONSUMER_ID',
});
await aleoClient.initNetwork();

const account = aleoClient.accountFromPrivateKey('APrivateKey1zkp...');
await aleoClient.registerAccountForRecordScanning(account);

const records = await aleoClient.fetchUnspentRecords(account, ['credits.aleo']);

const autoJoinClient = new AutoJoinClient(aleoClient, account, BasicAutoJoinStrategy);
const joinedRecord = await autoJoinClient.joinRecords(records);
```

`joinRecords` validates that all input records share the same program, are owned by the same address, are supported by the strategy, and each have a `transactionId`. It throws a descriptive error if any condition fails or onchain confirmation times out.

Swap `BasicAutoJoinStrategy` for `BatchAutoJoinStrategy` to use the deployed wrappers instead — the rest of the API is identical.
