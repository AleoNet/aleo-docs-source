# The Aleo Curves

Aleo's cryptography is built on two elliptic curves that work together: **BLS12-377** for SNARK operations (outer layer) and **Edwards BLS12** for in-circuit cryptography (inner layer).

## Overview

The critical relationship between these curves:

```
BLS12-377 scalar field (Fr) = Edwards BLS12 base field (Fq)
8444461749428370424248824938781546531375899335154063827935233455917409239041
```

This means arithmetic inside a BLS12-377 proof (natively in Fr) can be expressed as native field operations on Edwards BLS12 — no expensive field emulation is needed. This enables efficient in-circuit cryptographic operations and proof composition.

| | Edwards BLS12 | BLS12-377 |
|---|---|---|
| **Curve Model** | Twisted Edwards | Short Weierstrass |
| **Pairing-Friendly** | No | Yes (embedding degree 12) |
| **Scalar Field** | 251 bits | 253 bits |
| **Base Field** | 253 bits | 377 bits |
| **G1 Compressed Size** | 32 bytes | 48 bytes |
| **G2 Compressed Size** | N/A | 96 bytes |
| **Primary Use** | Addresses, signatures, key derivation | SNARK proofs, polynomial commitments |

### Inner and Outer Layers

- **Outer layer (BLS12-377)**: The SNARK prover generates proofs over BLS12-377. Verification uses pairings on this curve. The Structured Reference String (SRS), KZG polynomial commitments, and proof aggregation all operate in BLS12-377.
- **Inner layer (Edwards BLS12)**: Key generation, signing, address derivation, and record encryption happen on Edwards BLS12. When these operations are proven inside a SNARK, the arithmetic is expressed as constraint equations over BLS12-377's Fr — which equals Edwards BLS12's Fq. No field mismatch, cheap constraints.

This is analogous to Zcash's Jubjub + BLS12-381 pairing, but Aleo's curve choices maximize FFT efficiency.

## Edwards BLS12

A Twisted Edwards curve **embedded inside BLS12-377**, with complete, exception-free addition laws.

### Curve Equation

```
-x² + y² = 1 + d·x²·y²
```

### Parameters

| Parameter | Value |
|---|---|
| `a` | -1 |
| `d` | 3021 |
| Base field (Fq) | BLS12-377's scalar field Fr (253 bits) |
| Cofactor | 4 |
| Compressed point size | 32 bytes (x-coordinate + sign bit for y) |

Because `a = -1`, multiplication by `a` is just negation — very cheap in circuit constraints. The curve is birationally equivalent to a Montgomery curve.

### Usage

- **Account addresses** — Aleo `aleo1...` addresses are points on this curve
- **Key derivation** — Private key → view key → address
- **Transaction signatures** — Authorization signing
- **Pedersen commitments** — Record commitments and serial number generation
- **Encryption** — Record and ciphertext encryption

## BLS12-377

A pairing-friendly curve in the Barreto-Lynn-Scott family with embedding degree 12. Its scalar field Fr has **2-adicity 47** (2^47 divides Fr - 1), required for efficient FFTs during proof generation.

### Curve Equation

**G1**: `y² = x³ + 1` over Fq (377-bit prime field)

### Fields

| Field | Size | Modulus |
|---|---|---|
| Fq (base field) | 377 bits | `258664426012969094010652733694893533536393512754914660539884262666720468348340822774968888139573360124440321458177` |
| Fr (scalar field) | 253 bits | `8444461749428370424248824938781546531375899335154063827935233455917409239041` |

### Subgroups

- **G1** — Points on `y² = x³ + 1` over Fq, cofactor approximately 2^94
- **G2** — Points on the D-type quadratic twist over Fq² (degree-2 extension)
- **GT** — Target group in Fq^12 (degree-12 extension)

### Pairing

BLS12-377 supports an **Optimal Ate pairing** via Miller loop + final exponentiation:

```
e(aP, Q) = e(P, aQ) = e(P, Q)^a
```

This bilinearity property is the mathematical foundation of the Varuna SNARK and the **SonicKZG10** polynomial commitment scheme.

### Usage

- **SNARK proof generation and verification** — Varuna operates over BLS12-377
- **Structured Reference String (SRS)** — Universal setup parameters
- **KZG polynomial commitments** — SonicKZG10 commitment scheme
- **Proof aggregation** — Batching multiple transition proofs

BLS12-377 was designed (in the [ZEXE paper](https://eprint.iacr.org/2018/962)) specifically for efficient proof composition alongside the BW6-761 curve.

## Keccak in snarkVM

snarkVM implements Keccak as a sponge construction `Sponge[f, pad, r]`, where the permutation `f = Keccak-f[1600]` operates on a 5×5 grid of 64-bit lanes (1600-bit state).

### Padding Variants

| Variant | Padding Suffix | `pad(M)` |
|---|---|---|
| Keccak | `0x01` | `M \|\| 0x01 \|\| 0x00...0x00 \|\| 0x80` |
| SHA-3 | `0x06` | `M \|\| 0x06 \|\| 0x00...0x00 \|\| 0x80` |
| SHAKE | `0x1F` | `M \|\| 0x1F \|\| 0x00...0x00 \|\| 0x80` |

### snarkVM Parameters

| Variant | Bitrate (r) | Capacity (c) |
|---|---|---|
| Keccak-256 / SHA3-256 | 1088 bits | 512 bits |
| SHA3-512 | 576 bits | 1024 bits |

The bitrate `r` determines how many bits are XORed per absorb step; the capacity `c = 1600 - r` provides the security margin.

## ECDSA Signatures for Transaction Authorization

Aleo smart contracts support secp256k1-based ECDSA [signature verification](/build/aleo-instructions/reference/cryptographic-operations#ecdsa-verification). A custodian can deploy a smart contract representing a virtual wallet authorized with ECDSA signatures instead of native Aleo signatures. An ephemeral throwaway Aleo private key is used to sign the transaction itself, but is not the authentication authority. A virtual smart contract wallet authorized this way can only hold public funds.

A working implementation is available in the [`virtual_wallet` Leo example](https://github.com/ProvableHQ/leo-examples/tree/main/virtual_wallet). This pattern is particularly useful for **custodians** who need to manage onchain assets using existing ECDSA key infrastructure (HSMs, Ethereum signing keys) without exposing a native Aleo private key as the authority. It is also the basis for the multisig administration model used by the [private stablecoin programs](/build/use-cases/private_stablecoins) deployed on Aleo mainnet, where ECDSA keys from external signers authorize sensitive onchain operations.
